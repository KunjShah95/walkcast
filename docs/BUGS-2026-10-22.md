## P1 — serious correctness, cost, or privacy

### P1-1. Standard cron schedules silently run every hour

**Where:** `packages/core/src/schedules.ts:48-57`; accepted by `apps/desktop/server/server.ts:1466` (`interval: b?.interval ?? b?.cron ?? b?.every`).

**Evidence:** `parseInterval` handles only `*` and `*/N` in the minute field. Every other 5-field cron expression falls through to `return 3600000`.

```
0 9 * * 1   → 1 hour   (should be Mondays 09:00)
0 0 * * *   → 1 hour   (should be daily)
30 14 * * * → 1 hour
```

The exposed-server guard only rejects intervals below 15 minutes, so 1 hour passes.

**Impact:** A daily or weekly recording runs 24 times a day instead of once. That burns the account's daily recording quota, disk, and any TTS/LLM spend, and the schedule looks "almost right" rather than broken.

**Fix:** Parse the five fields and compute a real next-fire time, or reject unsupported cron with a 400 instead of guessing. Store `nextRunAt`, not only an interval, and add tests for daily/weekly expressions.

### P1-2. Lease-expiry sweep fails jobs without writing the `job.completed` outbox row

**Where:** `packages/core/src/store/pg-store.ts:153-157`, `packages/core/src/store/file-store.ts:255-258`; the store contract says a terminal transition writes a `job.completed` delivery (`packages/core/src/store/types.ts:202-207`).

**Evidence:** Both `claim()` implementations do a bulk update:

```sql
update jobs set status = 'failed', error = 'The worker stopped responding too many times.',
  secret = null, finished_at = now(), locked_by = null, lease_until = null
where status = 'running' and lease_until < now() and attempts >= max_attempts
```

No outbox row is inserted. Normal terminal failure paths do enqueue one.

**Impact:** A job that crash-loops (`maxAttempts = 2`) disappears from the queue with no webhook. The customer's integration never learns it failed, and the dashboard's delivery log is empty for that job.

**Fix:** Select the expired jobs, update them, and insert their `job.completed` deliveries in one transaction (Postgres), or enqueue the deliveries inside the same FileStore write chain. Add a test that an exhausted lease produces exactly one terminal delivery.

### P1-3. A delivered webhook is POSTed again when the success bookkeeping fails

**Where:** `packages/core/src/webhooks.ts:104-116`.

**Evidence:**

```ts
try {
  await deliver(d, opts);
  await store.completeDelivery(d.id, workerId, { ok: true });
} catch (e) {
  const retryAt = d.attempts >= MAX_ATTEMPTS ? null : new Date(Date.now() + backoffMs(d.attempts));
  await store.completeDelivery(d.id, workerId, { ok: false, error, retryAt }).catch(() => undefined);
}
```

The `catch` covers both the POST and the bookkeeping call. If the POST succeeded (endpoint returned 200) but `completeDelivery({ok: true})` throws, the delivery is marked failed and retried.

**Impact:** Duplicate side effects for the customer — duplicate tickets, CRM leads, or Slack messages. At-least-once delivery is expected, but this duplicate is caused by a local database error, and the delivery record now says the successful POST failed.

**Fix:** Separate the POST failure from the bookkeeping failure. If `completeDelivery({ok: true})` fails, leave the lease to expire without marking it failed (or retry the completion idempotently). Send a stable delivery id in the POST so receivers can dedupe.

### P1-4. The documented `?embed=1` iframe is blocked by `X-Frame-Options`

**Where:** `apps/desktop/server/server.ts:452-461` and `1116-1119`; feature documented in `README.md:192-193`.

**Evidence:** Every `send()` response gets `X-Frame-Options: SAMEORIGIN`. The embed branch is sent through the same helper:

```ts
if (url.searchParams.get("embed") === "1") {
  return send(200, "text/html; charset=utf-8", embedPage({ ...page, openUrl: `${siteUrl}${base}` }));
}
```

A third-party page embedding the share link is therefore refused by the browser.

**Impact:** The "one line of `<iframe>` for your own site" feature renders a blank frame on every external site. A same-origin iframe works, which hides the bug in local testing.

**Fix:** For the embed response only, omit `X-Frame-Options` and set `Content-Security-Policy: frame-ancestors *` (or an operator-configured allowlist). Keep `SAMEORIGIN` on the app shell and dashboard.

### P1-5. Journey recordings ignore `maxSeconds` and `maxPages`

**Where:** `packages/core/src/record/site.ts:560-571`, `followJourney` at `450-487`; the budgeted page loop starts at `575`.

**Evidence:** The journey branch runs before the budgeted loop and returns immediately:

```ts
if (journey.length > 0) {
  await followJourney(...);
  return "pages";
}
```

`followJourney` checks `options.signal` between steps but never `deadline` or `options.maxPages`. The closing line always says "Followed N steps".

**Impact:** A user who selects a 60-second or 5-page limit can get a multi-minute journey with unlimited page visits. That defeats the cost/time guard and can fill the media directory. The recording also reports the wrong stop reason.

**Fix:** Pass the deadline and page cap into `followJourney`, check them between steps and before each page, return `time`/`pages` as the reason, and use that reason in the closing narration.

### P1-6. Cursor glide awaits `requestAnimationFrame` forever on a hidden page

**Where:** `packages/core/src/record/cursor.ts:70-80` and `116-121`.

**Evidence:** `glide()` returns a promise that only resolves when the rAF loop reaches `p >= 1`. `pointAt` awaits it through `page.evaluate`, which has no Playwright timeout:

```ts
await page.evaluate(
  ([cx, cy, ms]) => window.__wcCursor?.glide(cx, cy, ms),
  [tx, ty, GLIDE_MS],
).catch(() => undefined);
```

Chromium throttles or suspends rAF for background/occluded tabs. A popup or a page that loses visibility can stop the loop.

**Impact:** The recording stalls at the cursor move until the worker's lease/stall guard kills it. On a long job that means a lost recording and a stuck queue slot.

**Fix:** Resolve the page-side promise with a `setTimeout(done, ms + 100)` fallback, or race the `evaluate` against a Node timer. Pointer animation should never gate the recording's progress.

### P1-7. A missing cassette silently turns a replay into paid live calls

**Where:** `packages/core/src/lab/fixture.ts:186-189`.

**Evidence:**

```ts
const modelMode =
  spec.kind === "scripted" ? undefined
  : (options.modelMode ?? (sameAgent && cassette && existsSync(cassette) ? "replay" : "live"));
```

In the default mode, a missing cassette is not reported in `drift`; the run simply goes live. The fixture still records `manifest.original.model`, so the result looks like a replay.

**Impact:** An experiment or `lab replay` that should be free, deterministic, and offline makes real model calls. With a multi-trial experiment this can be dozens of paid runs, and the reported pass^k is live behaviour, not the recorded behaviour.

**Fix:** If `manifest.original.model` is present but the cassette file is missing, fail the replay or add a drift entry and require an explicit opt-in to fall back live.

### P1-8. A HAR that fails scrubbing stays on disk in raw form

**Where:** `packages/core/src/lab/runner.ts:308-320`.

**Evidence:** `finishHar` returns `null` from its `catch` without deleting `path`. The raw HAR remains in the run directory, even though the run's manifest only names it when scrubbing succeeded.

**Impact:** Cookies, authorization headers, and typed values that the scrubber would have replaced remain in a file that can be included in a run export or served with the run. The summary says there is no HAR, so nobody looks for it.

**Fix:** `rmSync(path, { force: true })` in the catch, or write the scrubbed HAR to a temp file and replace the original only on success. Log the failure so it is visible.

### P1-9. Experiment detection and false-positive rates count agent/harness errors

**Where:** `packages/core/src/lab/experiment.ts:84-100` and `137-145`; `packages/core/src/lab/classifier.ts:341-377`.

**Evidence:** `detection` counts every run with `diagnosis.verdict === "fail"`, and `falsePositives` counts every clean run that failed. The classifier produces `verdict: "fail"` for `agent-error` and `budget-exhausted` causes. Phase 2 explicitly excludes `r.agentError` at `experiment.ts:104`, so the two phases disagree.

**Impact:** A model error, budget stop, or browser crash is reported as the baseline "detecting" a fault, and a clean run that hit the same harness error is reported as a false positive. Detection accuracy and FP rate are therefore wrong, and a broken agent can look like a better detector.

**Fix:** Exclude `agentError` and budget-exhausted runs from detection and FP denominators (or give them a separate `harness-error` verdict) and report their count explicitly.

### P1-10. ChatGPT requests and SSE reads have no timeout

**Where:** `packages/core/src/llm/chatgpt-responses.ts:107-142`; `packages/core/src/llm/rate-limit.ts:16-25`.

**Evidence:** `raw()` calls `fetch` and reads the SSE body with no `AbortSignal` or timeout. `TokenBucket.acquire` loops until the bucket has `cost` tokens and has no abort path. If the stream stalls, or `cost > capacity`, the loop never ends.

**Impact:** One ChatGPT-backed run can occupy a worker indefinitely (until an external watchdog), with no result and partial plan usage consumed.

**Fix:** Use `AbortSignal.timeout` (and wire the run's abort signal) for the request and the reader; reject `cost > capacity` instead of waiting; add a bounded retry/backoff.

### P1-11. Cloud TTS audio downloads have no timeout

**Where:** `packages/core/src/record/voice.ts:520` (Murf) and `:585` (custom voice URL).

**Evidence:** The synthesis POST has `AbortSignal.timeout(60_000)`, but the subsequent audio download is a bare `fetch(json.audioFile)` / `fetch(url)`. Node's fetch has no default timeout.

**Impact:** A stalled CDN response hangs the recording job before ffmpeg runs. The job holds its lease until the stall guard, and the user sees a recording that never finishes.

**Fix:** Give downloads the same timeout (and abort signal as appropriate), and remove partial temp files on failure.

### P1-12. A failed `goto` is recorded as a second visit to the previous page

**Where:** `packages/core/src/record/site.ts:586-604`.

**Evidence:**

```ts
await tools.goto(next).catch(() => undefined);
await tools.waitForQuiet(400, 8000);
const status = await lastDocumentStatus(recorder, next);
...
pages.push({ url: page.url(), title: obs.title, status, ... });
```

On failure, `page.url()` is still the page the walk was on. `lastDocumentStatus(next)` also returns `null` because the request never happened.

**Impact:** A duplicate page enters `pages`, the status is unknown, and the screenshot/captions describe the previous page while the walk claims to have visited the target. Insights and the guide then use the wrong page count and URL.

**Fix:** After `goto`, compare `normalize(page.url())` with `next`. If they differ, push a `skipped` entry (`reason: "navigation failed"`) or record a failed step, and do not add a `PageVisit` or a page screenshot.

## P2 — important, narrower impact

### P2-1. A blank or partial `LAB_PRICE_*` env disables the dollar ceiling

**Where:** `packages/core/src/llm/pricing.ts:49-54`.

`Number("")` is `0`, and `Number(undefined)` is `NaN` but is replaced with `0` for the missing side. A `.env` line such as `LAB_PRICE_INPUT_USD_PER_MTOK=` therefore produces `{ input: 0, output: 0 }`, and `estimateCost` returns 0 for every run. `--max-cost` never trips.

**Fix:** Treat empty/whitespace as unset, require both sides or neither, and return `null` for an incomplete pair.

### P2-2. FileStore's process lock is not atomic and survives `close()`

**Where:** `packages/core/src/store/file-store.ts:38-63` and `530-542`.

`existsSync(lock)` followed by `writeFileSync(lock, pid)` is a TOCTOU race: two processes can both pass. The lock is removed on normal process exit by the exit handler, but `close()` removes that handler and never unlinks the file, so a store closed while the process stays alive leaves a stale lock. The liveness check (`process.kill(pid, 0)`) can also succeed for a reused PID.

**Fix:** Create the lock with `O_EXCL`, store PID plus process start time, verify both on read, and unlink in `close()` when the contents match this process.

### P2-3. `worker.stop()` during `claim()` lets a newly claimed job run to completion

**Where:** `packages/core/src/jobs/worker.ts:167-215`.

`stop()` reads `this.current`, which is still `null` while the loop is awaiting `claim()`. It skips the grace/abort path and awaits `this.loop`; the claim then returns a job, and nothing re-checks `stopping` before `execute()`.

**Impact:** Shutdown can wait for a full recording instead of the 30 s grace period, and the job is not handed back to the queue.

**Fix:** After `claim()` returns, if `stopping`, release the job and break; or register the current job before awaiting, so `stop()` can abort it.

### P2-4. In-process secret sealing uses a per-process key and loses queued passwords on restart

**Where:** `packages/core/src/jobs/secret-box.ts:8-20`; `apps/desktop/server/server.ts:1333-1336`.

The server allows `seal(b.password)` when a worker is in-process even if `LAB_SECRET_KEY` is unset; `key()` then generates a random per-process key. A password queued before a restart cannot be opened afterwards, because the key is gone and `open()` throws.

**Impact:** Queued sign-in jobs fail after a restart (the worker's best-effort open falls back to no credentials), which looks like a site sign-in failure rather than a restart problem.

**Fix:** Require `LAB_SECRET_KEY` for any queued secret, or re-prompt for the password after a restart. Do not seal persistent queue data with the ephemeral key.

### P2-5. Voice preview cache and paid synthesis are unbounded

**Where:** `apps/desktop/server/server.ts:914-930`; `packages/core/src/record/media.ts:248-278`.

`cloudPreviews` is a `Map` with no size limit, keyed by `provider:voice:language`. `language` is accepted up to 20 characters and is not validated against known voices. Every cache miss calls the configured paid provider. The route requires auth, but any signed-in account can grow memory and spend the operator's keys without a rate limit.

**Fix:** LRU-cap the cache (e.g. 32 entries), validate provider/voice/language, and rate-limit preview synthesis per account.

### P2-6. robots.txt wildcards and `Allow` rules are ignored

**Where:** `packages/core/src/record/site.ts:582-585` and `770-787`.

`robotsDisallow` stores raw `Disallow:` values and the walk uses `pathname.startsWith(p)`. A rule such as `Disallow: /admin/*` never matches `/admin/settings`, and `Allow:` is not parsed at all. A plain `Disallow: /` over-blocks instead of applying a longer `Allow:` exception.

**Impact:** The recorder can visit paths the site explicitly disallowed, or skip paths the site allows. This is a policy/correctness bug (and a politeness problem), not a security boundary.

**Fix:** Compile wildcard rules to anchored regexes (`*` → `.*`, `$` → end), apply the longest matching rule with `Allow` winning ties, and add tests for `*`, `$`, and overrides.

### P2-7. An abort during browser startup is lost

**Where:** `packages/core/src/record/site.ts:181-196`.

The abort listener is registered at line 184 while `contextRef` is still `null` and is registered with `{ once: true }`. If the signal fires during `getBrowser()` (warm-browser launch) or `newContext()`, `abort()` does nothing and the listener is consumed. There is no `throwIfAborted` between context creation and the first `goto`/credential fill.

**Impact:** A user who cancels at "Starting the browser" still gets the browser, the sign-in, and the first page recorded. That is especially bad for a cancelled recording that types a password.

**Fix:** Check `signal.aborted` after context creation and before each action, and keep the listener until the context is torn down (or react to the already-aborted signal immediately).

### P2-8. One unactionable journey target aborts the whole recording

**Where:** `packages/core/src/record/site.ts:470-485`.

When `findControl` returns nothing, the step is recorded as `found: false` and the walk continues. But when it returns a target that `click`/`fill` cannot act on, the call throws out of `followJourney` and fails the entire recording.

**Fix:** Wrap the action in a try/catch, record a failed `journeyStep` with the error, and continue. A step that does not work is part of the walkthrough, as the comment already says.

### P2-9. Silent recordings ship overlapping captions

**Where:** `packages/core/src/record/narration.ts:114-115`; `packages/core/src/record/media.ts:55` and `63`.

`end` is `max(at + 1.5, next.at)`. When two actions are less than 1.5 s apart, the previous cue ends after the next begins. The narrated path retimes cues to the audio; the silent path writes them untimed. `test/record.test.ts:48-53` only asserts non-overlap inside `if (canNarrate())`, so the default no-voice run is untested.

**Fix:** Apply the same greedy retime (`start = max(start, previousEnd)`) before `toWebVtt` in both paths, and move the overlap assertion out of the `canNarrate()` guard.

### P2-10. A zoom-filter failure leaves no MP4 at all

**Where:** `packages/core/src/record/media.ts:62-71`; `packages/core/src/record/zoom.ts:130-156`.

`silent()` retries `muxSilent` with the same zoom filter. If the filter caused the failure (invalid `focus.json` width/height, or an ffmpeg build that rejects the filter), the retry fails too and the recording has only WebM + captions. `readFocus` validates only `moments` is an array, not the dimensions.

**Fix:** On a mux failure with zoom enabled, retry once with `zoomFilter = null`; validate numeric width/height/fps in `readFocus`.

### P2-11. Custom voices are server-global, not account-scoped

**Where:** `apps/desktop/server/server.ts:848-888`.

The list, upload, stream, and delete routes check authentication but never the owner. On a server with multiple accounts, any signed-in user can list and delete another account's uploaded voices.

**Fix:** Add an owner column/directory, or explicitly document custom voices as a server-wide resource and restrict deletion to the uploader (or an admin).

### P2-12. Voice upload fails across filesystems

**Where:** `apps/desktop/server/server.ts:859-865` and `1881-1887`.

`readBodyToTemp` writes to `os.tmpdir()`, then the route `renameSync`s the file into `data/voices`. On a Docker setup where `/tmp` and the data volume are different mounts (or on Windows with the data root on another drive), `rename` throws `EXDEV`.

**Fix:** Create the temp file inside the destination directory (or fall back to `copyFile` + `unlink`).

### P2-13. The idempotency key is minted per call, so it never deduplicates retries

**Where:** `apps/desktop/dashboard/src/lib/api.ts:155-157`.

`submitForResult` creates `crypto.randomUUID()` on every invocation. A double-click or a retried POST gets a new key, so `jobByKey` finds nothing. The comment says the key makes a double-click start one job.

**Fix:** Generate the key once per form submission and reuse it for retries, or dedupe by a content hash plus a short window.

### P2-14. FileStore acknowledges an enqueue before the debounced persist

**Where:** `packages/core/src/store/file-store.ts:82-103`.

`write()` mutates memory and schedules a 50 ms persist, then resolves. The server can return 202 before the job is on disk. A crash or `SIGKILL` in that window loses the job (and its secret), while the client has a job id that will never appear.

**Fix:** Persist (and fsync) before resolving for enqueue, or make the ack wait for the timer's persist.

## Test-suite failures (not counted as product bugs)

The full run had three failures. The web-build failures reproduce as a shared-output isolation issue; the record timeout is consistent with parallel load. Neither points at a recorder hang.

### `test/web-build.test.ts` — stale shared `dist/web`

- Failing tests: "the machine-readable files an agent needs are published and linked" and "answer engines are told where the answer is".
- Error: `dist/web/index.html has no <div id="root"></div> to fill` at `apps/web/build.ts:229`.
- `apps/web/build.ts:227` reads `dist/web/index.html` as the template **after** the client build. If the file is a previous run's prerendered page, the marker check throws. The script trusts a shared, mutable output directory.
- Reproduction: first isolated run failed 3/7; two later isolated runs passed 7/7. The full suite failed both tests.
- Fix: clean `dist/web` before building (or build to a unique temp directory and swap), and make the test use its own output directory. A clear "template missing" error would also help.

### `test/record.test.ts` — timeout under parallel load

- Failing test: "signs in, browses same-origin pages, narrates, and never writes the password".
- Timeout is 180 s; the same test passes standalone in ~86.5 s. The full suite runs browser/ffmpeg-heavy files in parallel on this machine.
- This looks like contention, not a hang in the recorder. It should still be made reliable: raise the test timeout, or lower `--test-concurrency` in CI.

`npm run typecheck` and `npm run lint` are green; these are runner/isolation issues.

## Checked and excluded

These were reported by parallel reviews but do not hold in the current tree:

- **Quota not refunded** — the submit path refunds every quota it charged on a later refusal (`apps/desktop/server/server.ts:1300-1344`).
- **Guide reflects the request `Host` header** — the Markdown guide uses the configured `siteUrl`, not `req.headers.host` (`server.ts:479-481`).
- **Action shots and `focus.json` are not published** — both are included in the worker's upload list (`worker.ts:357-369`).
- **SSRF DNS-rebinding TOCTOU in the recorder** — the recorder reaches the web through a guard proxy that checks the address on each connection (`site.ts:185-194`); webhooks use the pinned `guardedPost` path.
- **Chromium sandbox defaults off** — this is a documented Fargate tradeoff (`docs/DEPLOY-AWS.md:128`), not an accidental regression. It is still a hardening item if the recorder is exposed to untrusted URLs; consider a sandbox where the platform allows it.
- **Insights claims a clean bill of health with no segments** — `findingsFor` returns the zero-pages warning before the clean note, so an empty trace cannot produce the claim.
